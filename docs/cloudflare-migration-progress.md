## Inventory findings governing M1–M3

The async conversion touches every database-backed route, matching and session persistence. Runtime filesystem dependencies are the sql.js database and Notion key-file fallback. Both must leave the Worker runtime. Four tables have user-visible `rowid` ordering: plan entries, shopping items, recurring groceries and dinner staples.

Independent source review established these accepted input envelopes:

| Path | Current contract and migration consequence |
|---|---|
| Library import | 5MiB body, 1,000 options; ingredient count and field lengths otherwise unbounded. A single field can exceed D1's 2MB row/value limit. An accepted minimal fixture can contain 169,122 ingredient rows in a 5,242,875-byte request. Bounded JSON chunks alone do not solve oversized final fields. |
| Notion | 100 recipes, 1,000 ingredients per recipe; 10,000 total blocks includes validation replay. Maximum ingredient envelope is 4,975 across five recipes under minimum format overhead. |
| Planning repeat | 500 selected entries can each snapshot an imported recipe. Use set-based SQL; a theoretical 84,561,000-row copy needs an explicit capacity assessment. |
| Other selections | 500 recurring templates, 1,000 shopping IDs; session pool and ballot counts have no explicit cap beyond the ordinary 100KiB request body. Avoid dynamic parameter lists. |

Required concurrency coverage includes stale login-session `set` after logout (in addition to touch), expired-session deletion racing touch, duplicate registration after bcrypt, simultaneous library import/create/rename/restore, both close routes, Notion activation versus session creation, and shopping PATCH updating only supplied fields. Remove snapshot compensation; never restore an old sql.js snapshot across an await. Fetch library ingredients and Notion mappings in grouped queries to avoid the invocation query ceiling.
