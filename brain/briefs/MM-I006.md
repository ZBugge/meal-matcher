# MM-I006 — Personal family food app / PWA

2026-10-14, America/New_York. Assessment requested by Zach; no product implementation authorized in this turn.

## Short answer

Keep the React/Vite client, Express API, SQLite database, recipes, and swipe matching. Shift the product's center from sessions to a shared household recipe library and persistent meal plan. Add shopping-list state and a phone cooking view; make the existing web app installable. Solo planning must work without creating a voting session. Scale and distribution are no longer product goals.

Mission, based on Zach's stated direction: store the family's recipes, agree on meals for a day or week, turn the plan into a shopping list, and use the recipes while cooking. Everything else supports this loop. See [MM-D005](../DECISIONS.md#mm-d005).

## Original wording and intent

Meaningful excerpts from Zach's request:

> I'm no longer interested in, like, distributing it, really. I'm just going to use this as a personal home app that I'm going to iterate on very quickly.

> I want, like, very little guardrails, and I want to essentially redesign it as a PWA that I can have on my phone, perhaps my wife's phone.

> We'll just swipe on a bunch of meals and agree on, like three or four ... take off things that I already have in the house ... either go to Whole Foods for an order or get the food for the week all at once.

> I want to be able to use this as a place to store recipes so that I can in advance agree on what we're going to eat for a given day or week and use that to construct a shopping list, and then go in and actually use it to look at the recipes while I'm cooking. Everything should come downstream of that.

Takeout should support the same decision/planning purpose. The primary users are Zach and his wife, often Zach alone. Household sharing, fast changes, and practical phone use matter more than generalized accounts or large-group flows.

## Verified current setup

- `client/src/App.tsx`: `/` opens the public quick-session flow; the protected dashboard combines library/session management. There are no plan or shopping-list routes.
- `server/src/routes/meals.ts`, `server/src/services/recipe.ts`, and `server/src/db/schema.ts`: recipes already have instructions, ordered ingredient rows with free-text amounts, private notes, validated full-recipe paste, and versioned library import/export. Meal ownership is one `host_id`; recipe access is authenticated and ownership checked.
- `client/src/components/RecipeViewer.tsx`: recipe reading exists as a scrolling modal with ingredients and instructions. A dedicated mobile cooking page is an improvement, not a new recipe-storage system.
- `server/src/routes/sessions.ts` and `server/src/db/schema.ts`: sessions currently select one final meal; `session_history` is one record per session. The existing vote/ranking logic can be reused to pick several candidates for a separate plan.
- Planning choices should not imply meals have already been cooked. Preserve a distinction between planned entries and selection/cooking history when integrating the new flow.
- `client/src/pages/JoinSession.tsx` and `SwipeSession.tsx`: participants are session-specific, with browser recovery; these are not persistent household member identities or shared recipe permissions.
- `client/index.html`, `client/vite.config.ts`, and source/config searches: no web-app manifest, registered service worker, persistent plan/list entities, household model, or servings model was found.
- `server/src/index.ts`: cookie expiry is seven days and session storage is the default memory store. Frequent server restarts currently lose login sessions; reliable phone access would benefit from persistent login storage.

Live deployment, remote freshness, and production data were not inspected. This is an assessment of the local implementation.

## Recommended changes, not committed scope

1. Replace the session-first entry point with This Week, Recipes, Shopping, and Takeout navigation. Show today's meal and direct cooking access. Public quick sessions can be secondary; avoid spending the first increment deleting them.
2. Treat the product as one household. Start with one family login if desired and separate person profiles for voting; separate accounts need explicit access to the same household library. Do not expose private recipe fields through guest voting endpoints. Both phones should see and edit the same plan and shopping list.
3. Add saved plans with multiple entries, optional assigned dates, and recipe/takeout references. A swipe session helps choose entries; the plan remains usable and editable without a session. Choose three or four meals before requiring exact weekday assignments. Consider leftovers/free-text entries when useful, not as a prerequisite. Mixed home/takeout entries in a week do not require mixing existing voting pools.
4. Generate saved shopping rows from home-meal ingredients, retaining the recipe source and distinct states for needed, already have, and purchased. Permit extra groceries and manual edits. Preserve list edits/checks when the plan changes; show additions/removals rather than replacing the list silently. Existing amounts are text, so retain original units and permit manual duplicate merging first; automated conversion and serving scaling need further design.
5. Add a dedicated recipe/cooking view reachable from the plan and library, with readable text and large controls. Screen-awake behavior and step tracking are possible later polish.
6. Add app manifest/icons, standalone launch, HTTPS deployment, and phone navigation. Installation and offline behavior are separate capabilities. Cache selected recipes/plan/list for offline reading; offline checklist edits require deliberate local persistence and sync handling. Start with online shared edits rather than introducing a full offline synchronization framework.
7. Keep takeout as a plan-entry kind that contributes no grocery ingredients. Reuse category voting first; concrete favorite restaurants and ordering links can follow. Direct Whole Foods cart construction is a separate integration to investigate after the list works; start with a readable/copyable list.

Keep one deployed server/database, basic private access, and backups. Favor small migrations and checks covering real household use rather than scale architecture or broad approval ceremonies. No hosting migration, native rewrite, new production dependency, or existing authentication removal is implied.

## Suggested sequence

First deliver one usable solo loop on a phone: add recipes, choose several, save a plan, generate/edit a shopping checklist, and open a planned recipe while cooking, with basic installation support. Then connect couple voting to multi-meal plan selection and verify both phones share state. Follow with takeout placement, offline convenience, and grocery-order handoff as actual usage reveals friction. This is a recommendation awaiting a build request, not a reprioritization of all existing backlog items.
